# Filmroll — build roadmap

A disposable camera for events. Guests join by QR with no account, shoot a limited
roll, and the album develops after the event.

Strategy: **clone the Once loop first, then ship the things Once is missing**
(Android, offline, moderation, video, web checkout).

---

## Sequencing rule that drives everything

An **App Clip cannot ship on its own**. Apple requires a full iOS app published on
the App Store before an App Clip can be attached to it, and QR-invoked App Clips are
capped at **15 MB uncompressed**. See `docs/app-clip.md`.

So the order is forced:

```
Web PWA (works on every phone today)
      -> Native iOS app (App Store)
            -> App Clip (QR, no-download iOS guests)
                  -> Android host app
```

Do not start with the App Clip. Build the web guest camera first — it is also the
permanent fallback for Android, desktop, and any iPhone that declines the clip.

## Phase 0 — Prototype `DONE`

Working end to end on `localhost:3000`.

- [x] Create a film (title, open hours, reveal hours, shot limit, guest cap)
- [x] Host dashboard with QR + copy join link
- [x] Guest joins by name, no account
- [x] Browser camera capture (`getUserMedia` + canvas)
- [x] Per-guest shot limit enforced server-side
- [x] Delayed reveal + "Develop now" host override
- [x] Gallery with per-shot attribution

Known prototype debt, all fixed in Phase 1:

- JSON file store (`data/films.json`) — not concurrent-safe
- Photos written to `public/uploads` — served unauthenticated, reveal is bypassable
  by guessing a URL
- QR generated by a third-party API — leaks every join URL off-domain
- `hostSecret` in `localStorage` — lost if the host clears the browser

## Phase 1 — Real foundation `DONE`

Goal: nothing is lost, nothing leaks, reveal is actually enforced.

- [x] Postgres + Alembic schema: `films`, `guests`, `shots`
- [x] Object storage (MinIO locally, S3/R2 in production) with **signed direct uploads** —
      bytes never pass through the API server
- [x] Signed read URLs that **403 before reveal**, server clock is the source of truth
- [x] Idempotent shot writes: client-generated `shot_id`, unique constraint, so a
      double-tap or a retry never burns two shots
- [x] Derivatives worker: display WebP thumbnail, EXIF stripped, untouched original
- [x] Self-hosted QR generation (drop the third-party endpoint)
- [x] Host session: magic link email, replacing `localStorage` as the only copy
- [x] Rate limiting + upload size/type validation + EXIF strip on public derivatives
- [x] Structured logging: join funnel, upload success rate, queue depth
- [x] Event-day dashboard (2026-10-05): `GET /v1/ops/summary` behind `OPS_TOKEN`,
      shown at `/ops` on the web. Join and upload funnel per window, processing
      backlog and queue depth, stack health, and every open or busy film

**Done when:** a film survives a server restart, a guest cannot see a photo before
reveal even with a direct URL, and two hosts creating films at once cannot clobber
each other. Met, except durable host auth which moves to Phase 3 with co-hosts.

## Phase 2 — Guest experience, PWA `DONE`

This is the differentiator. Venue Wi-Fi is the enemy.

- [x] Installable PWA (manifest, icons, standalone display)
- [x] **Offline-first capture**: photo saved to IndexedDB immediately, upload queued
- [x] Retry with exponential backoff when the connection returns (page must be open,
      or reopened — iOS will not run Background Sync)
- [x] Visible queue state: "3 photos waiting to upload"
- [x] Resumable upload: fresh presigned URL on each PUT retry (same shot id; JPEGs skip S3 multipart)
- [x] Live filter preview via WebGL shader, developed into the copies guests see and
      save by the worker (originals stay clean for the ZIP)
- [x] Optional date stamp printed on developed photos, toggled by the host
- [x] Front/back camera switch
- [x] Flash/torch and zoom
- [x] Shot counter that feels like film ("8 left")
- [x] i18n: EN, ES, FR minimum
- [x] Accessibility pass — the "grandpa test": join to first photo under 30 seconds

**Done when:** you can put the phone in airplane mode, take 8 photos, re-enable
Wi-Fi, and all 8 arrive. The queue does this while the film page is open, and
again if the guest reopens it later. A killed iOS tab will not drain in the
background; that is a platform limit, not a missing retry.

## Phase 3 — Host tools `DONE`

- [x] Host dashboard: live guest count, shot count, upload health
- [x] **Moderation**: one-tap hide (and unhide), hidden photos never fan out
- [x] Co-hosts (couple + planner) and a read-only photographer seat
- [x] Print-ready QR table cards as PDF (table + signage sizes) plus a browser print page
      (four cards to an A4 or Letter sheet, ink on white, cut along the dashes)
- [x] Bulk **ZIP download of originals** (hidden shots omitted, media worker)
- [x] Extend film time, raise guest cap, adjust shot limit mid-event (Extend never runs
      past a fixed develop time on its own; change the develop time first)
- [x] Change the develop time after create: when the camera closes, next morning at
      10:00, or (web) any time after the close
- [x] Reveal scheduling + "develop now"
- [x] Instant reveal (live gallery from the first shot)
- [x] Guest can delete their own photo
- [x] Host can delete the whole film, with a grace period before erasure
- [x] Optional join PIN, so a photographed QR card is not enough to get in
- [x] Guests can report a photo to the host
- [x] Private vs shared gallery (default shared; private guests only see their own shots)
- [x] Reveal notification (email) the morning after
- [x] Reveal push to guests who joined from the app
- [x] Remove a guest (2026-10-05, Once has it): their camera stops at once, their
      seat goes back to the room, and their photos are hidden unless the host keeps
      them. No accounts, so a removed person can scan again; a join PIN keeps them out
- [x] Camera styles (2026-10-05, Once has it): warm, faded and mono. The film carries
      its style's constants so the web viewfinder draws exactly what develops;
      changeable until the album opens, re-rendering the roll like the date stamp
- [x] Once-style "warm film" redesign of every screen from the approved prototype
      (2026-10-04): web guest and host, app guest and host, the venue slideshow and
      the print page. Same flows and API; new look, a landing page, a three-step
      create on web and a one-screen create in the app
- [ ] Ephemeral clip notification (Phase 5)

**Done when:** a host can kill a bad photo in one tap before 150 phones see it.
Met: the host inbox shows photos *before* reveal, with signed URLs that the
public gallery will not mint.

**Instant reveal** is a live gallery, not a second reveal mechanism. Creation
stamps `reveal_at` to now so the existing SQL predicate
(`revealed_at IS NOT NULL OR now() >= reveal_at`) is already true. Hide still
works. The flag cannot be turned off later: guests cannot un-see a photo. A live
film is skipped by the "your film has developed" email, which would otherwise
land seconds after create.

**Private vs shared** is who sees whom after develop, not a second reveal.
Shared (the default) is one album. Private mints signed URLs only for the
calling guest's own shots; the host inbox and ZIP still hold the whole roll.
Unlike instant reveal this can be PATCHed later: going private does not un-see
a URL that already expired, and going shared is a deliberate host action. A
host token on `GET /gallery` must not unlock other people's photos — that is
what the inbox is for.

**Reporting** is a signal, never an action. A report never hides anything: at a
party with a hundred guests, a handful of friends could otherwise agree to bury
a photograph the couple wanted, and moderation belongs to whoever is hosting.
What the count buys is the host's attention, which is the scarce resource when
they are on the dance floor. Reports are guest-scoped and one-per-guest, and the
host sees the count but never who raised it — a report must not start an
argument between two people at the same wedding.

**Reveal push** is for the guests holding a camera. The host already gets
email; a second channel to the same inbox would not help them on the dance
floor. Tokens live on the guest row, not an account, and instant films never
send one — they are born developed. Expo Go on current SDKs often cannot mint
a remote token; a development or App Store build is what actually delivers.
The ephemeral 8h/24h clip notice stays Phase 5 with the clip itself.

The **join PIN** is optional and exists for one threat: a QR card sits on a table
all evening, and anyone who photographs it can otherwise walk into a private
event. It is stored as an HMAC under `SECRET_KEY` rather than bcrypt — no work
factor saves a six-digit secret, but a database dump alone cannot test guesses,
and an attacker holding the app secret can forge guest tokens anyway. The online
attacker is bounded by the existing 20-joins-per-hour limiter instead.

Deleting a film is **invisible now, destroyed later**. `deleted_at` 404s the film
for guests and co-hosts the moment the host confirms; the objects survive
`DELETED_FILM_GRACE_DAYS` (30) because these are usually the only copies of the
photographs that exist. An hourly sweep then erases the objects, shots, and
guests, and stamps `purged_at`. The film row and its payments are deliberately
kept — a receipt is tax paperwork for a service that was actually delivered, and
hard-deleting the film would cascade it away.

Access beyond the creator is a **seat**: a revocable row that a token points at,
not an account. A co-host can moderate, develop, and resize the room; a
photographer can read the inbox and pull the ZIP and nothing else. Neither sees
the owner's receipts or can invite anyone. Authorisation re-reads the seat on
every request, so "remove the planner" is immediate rather than a year-long wait
for a JWT to expire.

## Phase 4 — Money `DONE` (Nepal payment methods open)

Charge for **capacity and artifacts**, never per shutter press.

- [x] Stripe Checkout on web for guest-cap tiers (free 5 → paid ladder)
- [x] Re-priced against Once (2026-10-04): 10 guests $2.99, 25 $4.99, 50 $14.99,
      100 $29.99, 150 $44.99, 250 $69.99; unlimited shots and video clips $9.99 each,
      keep-forever $14.99. Level with Once where hosts compare, cheaper for big weddings
- [x] Entitlement model: cap enforced server-side, upgrade mid-event
- [x] Add-ons: unlimited shots
- [x] Video pack add-on ($9.99: 3 clips per guest, up to 15s, on top of the photo roll)
- [x] Keep-forever add-on (12 months included otherwise; ZIP always free)
- [x] Receipts, refunds, VAT/tax handling
- [x] Storage policy that is honest: 12 months included, then paid keep-forever;
      host ZIP export always free
- [x] Month-11 retention email
- [ ] Local payment methods for Nepal (user requirement, 2026-10-05). Stripe does not
      onboard businesses based in Nepal, so a Nepal-run Filmroll cannot take money through
      the current Checkout at all. Likely Khalti and/or eSewa as a second provider on the
      same `payments` table, with an NPR price ladder. Waiting on a short design, the
      merchant accounts and NPR prices from the user

**Why web-first billing:** Stripe on the web keeps ~97% of the price. Apple IAP takes
15–30%. Selling the event on web and treating the app as the camera is the single
biggest margin decision in the product.

Local Checkout is fake until `STRIPE_SECRET_KEY` is set: the host still picks a
tier, the cap still rises, and no money moves. Production ignores the fake flag.

## Phase 5 — Native iOS + App Clip `IN PROGRESS`

Full spec in `docs/app-clip.md`. Summary of the order:

- [x] Expo guest app: join by code, native camera, gallery after develop
- [x] Expo host: create film, share code + QR (full dashboard still on web)
- [x] Expo guest offline upload queue (JPEG on disk, drain when the app is open)
- [x] Host management in the native app (moderation, reveal, export, caps — Stripe upgrades stay on web until StoreKit)
- [ ] StoreKit 2 IAP in the **full app only** (App Clips cannot do IAP)
- [ ] **Publish the full app to the App Store** — hard prerequisite
- [ ] App Clip target, budget **≤15 MB uncompressed** (QR invocation limit)
- [ ] `Associated Domains` entitlement: `appclips:filmroll.app`
- [x] Serve `/.well-known/apple-app-site-association` with the `appclips` key
- [ ] Advanced App Clip Experience in App Store Connect, URL prefix
      `https://filmroll.app/f/`
- [ ] Clip reads `NSUserActivity.webpageURL` → parses film code → joins → camera
- [ ] Handoff clip → full app (App Group + "Get the full app" overlay)
- [ ] Ephemeral notification permission (8h/24h) for the reveal
- [ ] Optional: App Clip Codes (Apple's visual code) for premium printed cards
- [x] Smart App Banner on the web page (when `NEXT_PUBLIC_IOS_APP_STORE_ID` is set)

**Done when:** scanning the printed QR on an iPhone opens the camera card without an
App Store download, and the same QR on Android opens the PWA.

## Phase 6 — Android + moat `P2`

- [x] Android host app — the same Expo app (host + guest) runs on Android; App Links
      via `/.well-known/assetlinks.json`. Play Store listing waits on the same
      production URLs as the App Store build
- [x] Guest video clips, up to 15s, hard-capped, transcoded async — separate
      per-guest clip allowance, gated on the video pack; web (MediaRecorder) and
      the Expo app (expo-camera + expo-video); microphone asked only on first record.
      The media worker trims to 15s and re-encodes to H.264/AAC MP4 with metadata
      stripped, plus a poster frame; a clip is never shown before that
- [x] Live slideshow URL for a venue screen / projector — `/f/{code}/slideshow`,
      public gallery only; newest unseen shots first, then a cycle; clips play
      muted and hold the wall until they end; photos use the 1280 px derivative.
      Host dashboard and the mobile host Settings tab open the URL. A private
      gallery has no wall (the join QR stays up so guests can still shoot).
- [ ] Recap video worker: 45–90s, music bed, face/motion selection. **Paused
      2026-10-04 by the user:** it could change the business model, and the focus is
      the photo loop. Guest video stays short clips with no music or editing
      (Once's is widely reviewed as too short — this is a real opening)
- [x] Hearts in the album (2026-10-05, pulled forward; Once does not advertise likes): one per guest
      per photo, counted but never named, a "Most loved" order, and counts in the
      host inbox as the print shortlist
- [x] Camera-roll upload (2026-10-05; Once lacks it, POV has it): a host toggle, off by
      default. Each photo spends a shot from the same roll, and they are accepted after the
      camera closes until the album opens. Clients re-encode the pick (GPS and all EXIF
      gone, longest edge 4096 px) and send the photo's own date for the stamp. The host
      inbox marks them. Not in the App Clip (no photo-library access there)
- [ ] Multiple rolls per event (ceremony / cocktail / dance floor)
- [ ] Photobook + print partner
- [ ] Brand event pack: rights checkbox, usage export, analytics
- [ ] Planner / venue white-label licensing

## Effort estimate

Rough, for one full-time developer. Halve Phases 1–4 with two people.

| Phase | Scope | Estimate |
|---|---|---|
| 1 | Real foundation | 2–3 weeks |
| 2 | PWA + offline | 2–3 weeks |
| 3 | Host tools | 2 weeks |
| 4 | Payments | 1–2 weeks |
| 5 | iOS app + App Clip | 5–8 weeks (incl. review) |
| 6 | Android + moat | 6+ weeks |

**First public launch = Phases 1–4.** That is a complete, sellable product on every
phone, with no App Store dependency at all. Phase 5 is an acquisition upgrade for
iPhone guests, not a prerequisite for revenue.

## Definition of done for v1

1. 100 guests can join a single film from a printed QR
2. Photos survive dead venue Wi-Fi
3. Host can hide a photo before anyone else sees it
4. Gallery unlocks at the reveal time and not one second earlier
5. Host downloads a ZIP of clean originals
6. The couple paid on the web, not through a 30% tax

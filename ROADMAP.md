# Filmroll — build roadmap

A disposable camera for events. Guests join by QR with no account, shoot a limited
roll, and the album develops after the event.

Strategy: **clone the Once loop first, then ship the things Once is missing**
(Android, offline, moderation, video, web checkout).

---

## Sequencing rule that drives everything

An **App Clip cannot ship on its own**. Apple requires a full iOS app published on
the App Store before an App Clip can be attached to it, and QR-invoked App Clips are
capped at **15 MB uncompressed**. See `docs/app-clip.md`.

So the order is forced:

```
Web PWA (works on every phone today)
      -> Native iOS app (App Store)
            -> App Clip (QR, no-download iOS guests)
                  -> Android host app
```

Do not start with the App Clip. Build the web guest camera first — it is also the
permanent fallback for Android, desktop, and any iPhone that declines the clip.

---

## Phase 0 — Prototype `DONE`

Working end to end on `localhost:3000`.

- [x] Create a film (title, open hours, reveal hours, shot limit, guest cap)
- [x] Host dashboard with QR + copy join link
- [x] Guest joins by name, no account
- [x] Browser camera capture (`getUserMedia` + canvas)
- [x] Per-guest shot limit enforced server-side
- [x] Delayed reveal + "Develop now" host override
- [x] Gallery with per-shot attribution

Known prototype debt, all fixed in Phase 1:

- JSON file store (`data/films.json`) — not concurrent-safe
- Photos written to `public/uploads` — served unauthenticated, reveal is bypassable
  by guessing a URL
- QR generated by a third-party API — leaks every join URL off-domain
- `hostSecret` in `localStorage` — lost if the host clears the browser

---

## Phase 1 — Real foundation `P0`

Goal: nothing is lost, nothing leaks, reveal is actually enforced.

- [ ] Postgres (Supabase) + Drizzle schema: `films`, `guests`, `shots`, `purchases`,
      `moderation_events`, `co_hosts`
- [ ] Object storage (Supabase Storage / S3 / R2) with **signed direct uploads** —
      bytes never pass through the API server
- [ ] Signed read URLs that **403 before reveal**, server clock is the source of truth
- [ ] Idempotent shot writes: client-generated `shot_id`, unique constraint, so a
      double-tap or a retry never burns two shots
- [ ] Derivatives worker: `thumb` (400px webp), `display` (1600px webp), untouched
      `original` retained
- [ ] Self-hosted QR generation (drop the third-party endpoint)
- [ ] Host session: magic link email or Sign in with Apple, replacing `localStorage`
- [ ] Rate limiting + upload size/type validation + EXIF strip on public derivatives
- [ ] Structured logging: join funnel, upload success rate, queue depth

**Done when:** a film survives a server restart, a guest cannot see a photo before
reveal even with a direct URL, and two hosts creating films at once cannot clobber
each other.

---

## Phase 2 — Guest experience, PWA `P0`

This is the differentiator. Venue Wi-Fi is the enemy.

- [ ] Installable PWA (manifest, icons, standalone display)
- [ ] **Offline-first capture**: photo saved to IndexedDB immediately, upload queued
- [ ] Service worker background sync + retry with exponential backoff
- [ ] Visible queue state: "3 photos waiting to upload"
- [ ] Resumable/chunked upload for large files on bad connections
- [ ] Live filter preview via WebGL shader (look applied at capture *preview*, never
      baked into the stored original)
- [ ] Front/back camera switch, flash/torch, zoom
- [ ] Shot counter that feels like film ("8 left")
- [ ] i18n: EN, ES, FR minimum
- [ ] Accessibility pass — the "grandpa test": join to first photo under 30 seconds

**Done when:** you can put the phone in airplane mode, take 8 photos, re-enable
Wi-Fi, and all 8 arrive.

---

## Phase 3 — Host tools `P1`

- [ ] Host dashboard: live guest count, shot count, upload health
- [ ] **Moderation**: one-tap hide, pending/approved states, hidden photos never
      fan out to other guests
- [ ] Co-hosts (couple + planner) and a read-only photographer seat
- [ ] Print-ready QR table cards as PDF (2 sizes, event name, short code)
- [ ] Bulk **ZIP download of originals**
- [ ] Extend film time, raise guest cap, adjust shot limit mid-event
- [ ] Reveal scheduling + "develop now"
- [ ] Guest can delete their own photo
- [ ] Reveal notification (email/push) the morning after

**Done when:** a host can kill a bad photo in one tap before 150 phones see it.

---

## Phase 4 — Money `P1`

Charge for **capacity and artifacts**, never per shutter press.

- [ ] Stripe Checkout on web for guest-cap tiers (free 5 → paid ladder)
- [ ] Entitlement model: cap enforced server-side, upgrade mid-event
- [ ] Add-ons: unlimited shots, video pack, keep-forever storage
- [ ] Receipts, refunds, VAT/tax handling
- [ ] Storage policy that is honest: 12 months included, then paid keep-forever;
      host ZIP export always free
- [ ] Month-11 retention email

**Why web-first billing:** Stripe on the web keeps ~97% of the price. Apple IAP takes
15–30%. Selling the event on web and treating the app as the camera is the single
biggest margin decision in the product.

---

## Phase 5 — Native iOS + App Clip `P1`

Full spec in `docs/app-clip.md`. Summary of the order:

- [ ] SwiftUI full app: host management + guest camera + gallery
- [ ] StoreKit 2 IAP in the **full app only** (App Clips cannot do IAP)
- [ ] **Publish the full app to the App Store** — hard prerequisite
- [ ] App Clip target, budget **≤15 MB uncompressed** (QR invocation limit)
- [ ] `Associated Domains` entitlement: `appclips:filmroll.app`
- [ ] Serve `/.well-known/apple-app-site-association` with the `appclips` key
- [ ] Advanced App Clip Experience in App Store Connect, URL prefix
      `https://filmroll.app/f/`
- [ ] Clip reads `NSUserActivity.webpageURL` → parses film code → joins → camera
- [ ] Handoff clip → full app (App Group + "Get the full app" overlay)
- [ ] Ephemeral notification permission (8h/24h) for the reveal
- [ ] Optional: App Clip Codes (Apple's visual code) for premium printed cards
- [ ] Smart App Banner on the web page so iOS users are offered the clip

**Done when:** scanning the printed QR on an iPhone opens the camera card without an
App Store download, and the same QR on Android opens the PWA.

---

## Phase 6 — Android + moat `P2`

- [ ] Android host app (or keep host on web and skip this)
- [ ] Guest video clips, 5–15s, hard-capped, transcoded async
- [ ] Live slideshow URL for a venue screen / projector
- [ ] Recap video worker: 45–90s, music bed, face/motion selection
      (Once's is widely reviewed as too short — this is a real opening)
- [ ] Multiple rolls per event (ceremony / cocktail / dance floor)
- [ ] Photobook + print partner
- [ ] Brand event pack: rights checkbox, usage export, analytics
- [ ] Planner / venue white-label licensing

## Effort estimate

Rough, for one full-time developer. Halve Phases 1–4 with two people.

| Phase | Scope | Estimate |
|---|---|---|
| 1 | Real foundation | 2–3 weeks |
| 2 | PWA + offline | 2–3 weeks |
| 3 | Host tools | 2 weeks |
| 4 | Payments | 1–2 weeks |
| 5 | iOS app + App Clip | 5–8 weeks (incl. review) |
| 6 | Android + moat | 6+ weeks |

**First public launch = Phases 1–4.** That is a complete, sellable product on every
phone, with no App Store dependency at all. Phase 5 is an acquisition upgrade for
iPhone guests, not a prerequisite for revenue.

---

## Definition of done for v1

1. 100 guests can join a single film from a printed QR
2. Photos survive dead venue Wi-Fi
3. Host can hide a photo before anyone else sees it
4. Gallery unlocks at the reveal time and not one second earlier
5. Host downloads a ZIP of clean originals
6. The couple paid on the web, not through a 30% tax

# Continue Filmroll from the existing plan

Do **not** rewrite `ROADMAP.md` or start a new architecture. Clone the Once loop, then add what Once is missing. First public launch is Phases 1–4 (already the sellable web product). Phase 5 is an iPhone acquisition upgrade, not a revenue prerequisite.

**Workspace layout (changed 2026-10-05).** This parent repo ignores `web/`, `mobile/` and `backend/`; each is its own repo, so check changes with `git -C <repo> status`, not the parent's status. The Docker stack moved into `backend/`: `docker-compose*.yml`, `Makefile`, `scripts/` and the real `.env` (`backend/.env`). Run `docker compose …` from `backend/`; `make …` still works from here because the root `Makefile` forwards. Each repo has its own `.github/workflows/test.yml` and `.githooks/pre-push`. The parent showing `docker-compose.yml` or `scripts/` as deleted is expected: never restore them. Still no commits; the user handles git.

Before that (2026-10-05): **multiple rolls**, built on the user's "ok continue" after a short design with three choices, all taken as recommended: one QR with timed rolls (not a QR per roll), one reveal for the whole film, and a shot allowance per roll. Once has nothing like it (its only workaround is a second film: second QR, second payment, guests join twice); its own comparison blog credits GuestCam ("six main galleries with separate QR codes") and GuestPix ("separate albums for different wedding moments"). **Data model, and why it is shaped this way:** a migration that gave every existing film a roll row and rewrote every shot was blocked by the auto-mode safety check (it rewrites shared data), so the model is additive: a film with no `rolls` rows is one implicit roll (its own window and `shot_limit`, shots with null `roll_id`), and rows only appear when a host splits a film, at which point that film's shots are assigned to the roll they were taken in (`rolls.replace_rolls`). Migration `9e2d4b6a8c15` only adds the table, a nullable `shots.roll_id` (`ON DELETE SET NULL`) and an index. `app/services/rolls.py` holds the rules (1 to 6 rolls, no overlaps, names required once there are two, a roll with photos cannot be removed, a roll cannot shrink below a guest's use) and keeps `Film.closes_at` = last close and `Film.shot_limit` = total, so joining, Extend and old clients still work; PATCH `closes_at` moves the last roll, PATCH `shot_limit` edits a single roll and is refused (409) on a split film. Reserve counts per roll in one SQL statement (`roll_id IS NOT DISTINCT FROM`, limit from the roll or else the film); between rolls a camera shot is **409 "no roll is open right now"**, never 410 (clients treat 410 as the camera closing for good); a camera-roll photo goes to `roll_for_moment` of its taken time. `shots_remaining` is the open (or next) roll's; `GET /me` adds per-roll `rolls`. `PUT /v1/films/{code}/rolls` (host, co-host) takes the whole list. Gallery and inbox photos carry `roll_id`; the ZIP has numbered folders per roll. Clients: `web/lib/rolls.ts` (mirrored in `mobile/src/rolls.ts`): the camera only opens while a roll is open, the camera header and roll screen show the open roll and its time left or "Party opens at …", a per-roll list ("1 of 4", Open now / Opens … / Closed) on split films, and roll tabs in the album. Split films count taken shots from the server (like unlimited ones). Host: web Settings → Rolls (`components/host/RollsEditor.tsx`: "Split into rolls" seeds Ceremony/Party from the rest of the film, datetime-local rows, API errors shown as is); the film-wide shot stepper becomes a pointer on split films. The app's host Settings shows the rolls read-only with "Edit on web" (a native date picker would be a new native dependency). Verified at 390 px on web and on the Android emulator (join, camera header, a real shot moving "1 of 4", between-rolls screen, album tabs, host row via a co-host seat). Not on iOS (no tap driver).

Before that (2026-10-05): **camera-roll upload**, chosen by the user from three options (Once lacks it, and a US App Store review of Once calls it the app's "ONE massive flaw"; POV has it). `films.camera_roll` (host toggle, off by default, on create and PATCH) and `shots.source` (`camera` / `library`), migration `3c8f1e6a9b27`. ## Invariants that survive every slice

- Photo bytes never transit Next.js or FastAPI; clients PUT to storage.
- Reveal is SQL: `revealed_at IS NOT NULL OR now() >= reveal_at` (database clock).
- Caps use `SELECT … FOR UPDATE` (guest row for shots, film row for joins).
- Client-generated shot UUIDs.
- Celery only `after_commit`. Queues `fast` vs `media`.
- Charge for capacity, never per shutter. Billing is web-first.
- `guest_cap <= entitled_guest_cap` is a DB check.
- No accounts anywhere. Extra access is a revocable seat row, never a login.
- Deletion hides immediately and erases after a grace window. Never hard-delete a film row: payments cascade off it and receipts are tax records.
